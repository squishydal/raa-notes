Phase 1: The Committing Workflow (Making a Commit)

When you type `git commit`, Git executes four hooks in a strict sequence:

```
[git commit] ➔ 1. pre-commit ➔ 2. prepare-commit-msg ➔ 3. commit-msg ➔ 4. post-commit
```

- **`pre-commit`**
    - **When it runs:** Right after you type `git commit`, before you type a message.
    - **What it does:** Inspects the _snapshot_ of the code you are about to commit.
    - **Use Case:** Runs a linter to check for syntax errors or scans files to ensure you didn't accidentally leave an API key or password exposed. If it finds an error, it stops the commit.
- **`prepare-commit-msg`**
    - **When it runs:** Right after `pre-commit`, before your text editor (like VS Code or Vim) opens up for you to type your commit message.
    - **What it does:** It modifies the _default_ text of the commit message programmatically.
    - **Use Case:** It looks at your current branch name (e.g., `feature/JIRA-404`), extracts `JIRA-404`, and prepends it to the empty text file so it's already there when your editor opens.
- **`commit-msg`**
    - **When it runs:** Right _after_ you finish typing your commit message and close the text editor.
    - **What it does:** Inspects the _text_ of the message you just wrote.
    - **Use Case:** Checks if your message follows rules (e.g., "Must start with `feat:`, `fix:`, or `docs:`"). If your message is just "fixed stuff", it rejects the commit and forces you to rewrite it.
- **`post-commit`**
    - **When it runs:** Immediately after the commit is successfully saved to your local history.
    - **What it does:** Notification and logging. It cannot stop the commit because the commit is already done.
    - **Use Case:** Sends a desktop notification saying "Commit successful!" or pings a local time-tracking software to log that you finished a task.

---

Phase 2: The Collaboration Workflow (Pushing & Pulling)

When you share your code with others on GitHub, GitLab, or Bitbucket.

- **`pre-push`**
    - **When it runs:** Right after you type `git push`, before any data is actually uploaded to the remote server.
    - **What it does:** Acts as a final local gatekeeper before your code goes public.
    - **Use Case:** Runs your full, heavy unit test suite or integration tests. If the tests fail, it blocks the push, saving you from breaking the main production branch or failing the CI/CD pipeline on GitHub.
- **`post-merge`**
    - **When it runs:** Right after a successful `git pull` or `git merge` completes.
    - **What it does:** Aligns your local project environment with the new code you just downloaded.
    - **Use Case:** If your teammate added a new npm package, this hook notices the change in `package.json` and automatically runs `npm install` for you in the background.

---

Phase 3: The Navigation Workflow (Switching Branches)

When you move around your repository.

- **`post-checkout`**
    - **When it runs:** Right after you successfully switch branches using `git checkout` or `git switch`.
    - **What it does:** Cleans up or sets up your directory based on the branch you just entered.
    - **Use Case:** If you switch from a heavy `development` branch to a clean `production` branch, this hook can automatically delete cached build files (like `.pyc` or `dist/` folders) so old compiled files don't conflict with your current branch.

# Server Side 

      The 3 Core Server-Side Hooks

When you run `git push`, the server processes the data through three distinct hook functions in this exact order:

```
[git push received] ➔ 1. pre-receive ➔ 2. update ➔ 3. post-receive
```

1. `pre-receive` (The Ultimate Gatekeeper)

- **When it runs:** As soon as the server receives a `git push`, before _any_ branches or references are actually updated on the server.
- **What it does:** It looks at the entire push payload (all branches, tags, and commits being uploaded at once). If it exits with a non-zero status, the **entire push is rejected**, and nothing changes on the server.
- **Exclusive Server Use Cases:**
    - **Enterprise Secret Scanning:** Scanning all incoming commits for hardcoded AWS keys, database passwords, or private SSH keys. If a secret is found, the server rejects the push to prevent a security breach.
    - **Enforcing Linear History:** Rejecting any push that contains merge commits to keep the git history perfectly flat.

2. `update` (The Branch Guard)

- **When it runs:** Right after `pre-receive`, but it executes **once for each branch** being pushed. If you push 3 branches at once, `pre-receive` runs once, but `update` runs 3 times.
- **What it does:** It allows or rejects changes on a branch-by-branch basis.
- **Exclusive Server Use Cases:**
    - **Access Control (Permissions):** Checking who is pushing. For example: "Is John allowed to force-push to the `main` branch? No? Reject his push to `main`, but let his push to `feature/login` succeed."
    - **Tag Protection:** Preventing developers from deleting or modifying release tags (e.g., `v1.0.0`) once they are pushed.

3. `post-receive` (The Automation Engine)

- **When it runs:** After all branches/tags have been successfully updated on the server.
- **What it does:** It cannot block the push anymore. It is strictly used to trigger external systems and downstream workflows.
- **Exclusive Server Use Cases:**
    - **CI/CD Triggers:** Signaling tools like Jenkins, TeamCity, or internal servers to start building the code and running automated tests.
    - **ChatOps & Alerts:** Pinging a Slack/Discord channel with a detailed layout of the new commits: _"User X just pushed 3 commits to `main`."_
    - **Ticket Status Updates:** Reading the commit messages (e.g., `"Fixes PROJ-456"`) and automatically moving that ticket to "Done" in Jira or Linear.
    - **Direct Deployment:** In simple setups (like Heroku or custom VPS), this hook copies the pushed files directly into the web server production directory (`/var/www/html`) to update the live website instantly.

### 🚇 Tunnel (SSH Port Forwarding)

A tunnel encapsulates one protocol inside another to traverse networks or secure traffic. The most common example is **SSH tunneling**, which uses the encrypted SSH connection to forward ports.

**Definition & How It Works:** It creates an encrypted channel between your local machine and a remote server. You can forward a local port to a remote service (Local Forwarding), or forward a remote port back to your local machine (Remote Forwarding).

**Use Case:** Accessing a database or internal web service that is not exposed to the public internet, without setting up a full VPN.

**Example (Local Port Forwarding):**  
Suppose you want to access a PostgreSQL database running on a remote server (`db.internal`) through a bastion host (`bastion.example.com`). You can map your local port `5432` to the remote database:

bash

ssh -L 5432:db.internal:5432 admin@bastion.example.com

After running this, connecting to `localhost:5432` on your machine will tunnel through the bastion to the database .[](https://raw.githubusercontent.com/OneUptime/blog/refs/heads/master/posts/2026-03-04-ssh-tunneling-port-forwarding-rhel-9/README.md#1)

### Reverse Proxy

A reverse proxy sits in front of one or more web servers (backends). Clients only talk to the proxy; the proxy decides which backend should handle the request.

**Definition & How It Works:** It accepts requests from clients, forwards them to the appropriate backend server, and returns the response. It hides the internal network topology from the outside world .[](https://svn.apache.org/repos/asf/httpd/httpd/tags/2.4.33/docs/manual/howto/reverse_proxy.xml)[](https://notes.kodekloud.com/docs/Nginx-For-Beginners/Intermediate-Config/Reverse-Proxy/page#tls-%2F-ssl-termination-and-end-to-end-encryption#1)

**Use Case:** Load balancing traffic across multiple application servers, terminating SSL/TLS encryption, or routing requests based on URL paths (e.g., `/api` goes to one server, `/images` to another).

**Example (Nginx Configuration):**  
Here is a basic Nginx configuration that forwards requests for `/` to a backend application running on port `3000`:

nginx

server {
    listen 80;
    server_name example.com;
    location / {
        proxy_pass http://localhost:3000;
    }
}

This tells Nginx to act as a reverse proxy, passing all traffic to your app server .[](https://notes.kodekloud.com/docs/Nginx-For-Beginners/Intermediate-Config/Reverse-Proxy/page#tls-%2F-ssl-termination-and-end-to-end-encryption#1)

1. The Proxy (Forward Proxy) = Your Personal Assistant 🕵️‍♂️

- **Who it protects:** **You** (the client/user).
- **The Analogy:** You want to buy something from a store, but you don't want the store to know who you are, or the store has banned you. You send your **Personal Assistant** to the store instead. The store sees the assistant, sells them the item, and the assistant brings it back to you. The store **never knows** you were the one who actually wanted the item.
- **Main Goal:** To hide the identity of the user, bypass content blocks, or filter what users can see (like a school blocking social media).

2. The Reverse Proxy = The Receptionist 🏢

- **Who it protects:** **The Website** (the server).
- **The Analogy:** A customer walks into a massive corporate building. They aren't allowed to wander around the back rooms where the servers or developers are. Instead, they must talk to the **Receptionist** at the front desk. The receptionist takes the request, goes to the back room to get the answer, and brings it back to the customer. The customer **never knows** which specific employee or room handled their request.
- **Main Goal:** To hide the identity/structure of the backend servers, balance heavy traffic (load balancing), and protect the website from hackers.

|**Primary Use Case**|Anonymity, bypassing office bans, web scraping.|Load balancing, DDoS protection (e.g., Cloudflare), SSL handling.|
