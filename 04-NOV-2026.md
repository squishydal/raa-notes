## Cyclomatic Complexity

Metric untuk mengukur tingkat kompleksitas suatu fungsi/code.

> [!answer] Definisi yang lebih tepat
> Cyclomatic Complexity (CC) = **jumlah jalur independen** yang mungkin dilalui lewat sebuah fungsi. Bukan "variabel a lewat berapa logic", tapi **berapa banyak percabangan keputusan** di dalam fungsi.
>
> Rumus praktis: **CC = jumlah decision point + 1**
>
> Yang dihitung sebagai decision point: `if`, `else if`, `for`, `while`, `case` (tiap case), `catch`, `&&`, `||`, `?:`.
> Yang tidak dihitung: `else` dan `default`.
>
> Kenapa penting:
> - CC tinggi = susah dibaca, susah di-test (minimal butuh sebanyak CC test case untuk cover semua jalur), rawan bug.
> - Angka umum: 1–10 sehat, 11–20 mulai kompleks, 20+ sebaiknya direfactor.

Contoh:
````javascript
function getErrorMessage(statusCode) {
    switch(statusCode) {
        case 400: return "Bad Request";
        case 401: return "Unauthorized";
        case 403: return "Forbidden";
        case 404: return "Not Found";
        // ... ada 15 case lainnya
        default: return "Unknown Error";
    }
}
````

Complexity-nya ±16 (di catatan), padahal guideline in-house hanya 9. Jadi kalau function kena error seperti ini, dipecah lagi fungsinya.

> [!answer] Hitungan & cara memperbaiki
> Dengan 4 case + 15 case lain = 19 `case` → CC = 19 + 1 = **20** (angka 16 di catatan kemungkinan dari jumlah case yang berbeda; konsepnya sama).
>
> Memecah fungsi itu valid, tapi untuk kasus *lookup* seperti ini cara terbaik adalah **ganti switch dengan tabel data**, CC turun jadi 1–2:
> ```javascript
> const ERROR_MESSAGES = {
>   400: "Bad Request",
>   401: "Unauthorized",
>   403: "Forbidden",
>   404: "Not Found",
>   // ...
> };
>
> function getErrorMessage(statusCode) {
>   return ERROR_MESSAGES[statusCode] ?? "Unknown Error";
> }
> ```
> Catatan: `??` dihitung 1 decision point, jadi CC = 2.
>
> Teknik refactor lain untuk CC tinggi:
> - **Early return / guard clause** (kurangi nesting)
> - **Extract function** (pecah jadi fungsi kecil, ini yang dimaksud guideline)
> - **Strategy / polymorphism** untuk logic bercabang berdasarkan tipe
> - Pecah kondisi `&&`/`||` panjang jadi fungsi bernama, misal `isEligible(user)`

## INTRODUCED Hover Lint

> Basically safeguard pertama sebelum nge-push; kalau tidak sesuai dengan guideline ya tidak akan bisa ngepush.

> [!answer] Konsep
> Ini pola **pre-commit / pre-push hook**: Git menjalankan script otomatis sebelum `commit`/`push`. Kalau lint (termasuk cek Cyclomatic Complexity ≤ 9) gagal, exit code ≠ 0 dan push dibatalkan. Tujuannya menangkap masalah di laptop sebelum sampai ke CI (Jenkins), jadi lebih cepat dan hemat resource.
>
> Alur:
> ```
> git push → .git/hooks/pre-push → jalankan lint → lulus? push lanjut : push ditolak
> ```
> Tools sejenis yang umum: `husky` + `lint-staged` (JS), `pre-commit` (Python/umum), atau script manual di `.git/hooks/`.
>
> ⚠️ "Hover Lint" kelihatannya tool in-house, jadi saya tidak bisa memastikan perintah install-nya. Isi bagian di bawah dari dokumentasi internal.

## Questions

### 1. `docker login` gagal, jawabannya "akan di-Throttle". Apa itu throttle?

> [!answer]
> **Throttle** = server sengaja **memperlambat atau membatasi** request dari satu sumber (IP/akun) kalau terlalu banyak dalam waktu tertentu. Sinonim dekat: **rate limiting**. Bedanya tipis: rate limit biasanya menolak (HTTP `429 Too Many Requests`), throttle bisa memperlambat atau menolak sementara.
>
> Analogi: pintu masuk konser yang hanya melepas 10 orang per menit, sisanya antre atau disuruh balik lagi.
>
> Konteks Docker: Docker Hub membatasi jumlah `pull` dan percobaan login per IP/akun. Kalau di kantor/kampus banyak orang berbagi 1 IP publik (NAT), kuota cepat habis, atau percobaan login berulang dianggap mencurigakan, dan hasilnya login/pull ditolak sementara (`toomanyrequests`).
>
> Solusi:
> - Tunggu beberapa saat lalu coba lagi.
> - Login dengan akun (kuota authenticated lebih besar dari anonymous), pakai Personal Access Token: `docker login -u <user>` lalu password = token.
> - Pakai **registry mirror / cache** internal kantor.
> - Jangan loop `docker login` di script.
>
> Besaran limit Docker Hub pernah berubah beberapa kali, cek halaman resmi Docker Hub "usage and limits" untuk angka terbaru.

### 2. Bagaimana CI/CD bekerja, khususnya Jenkins?

> [!answer]
> **CI (Continuous Integration)**: tiap perubahan code digabung sering ke repo utama dan langsung diverifikasi otomatis (build, lint, test).
> **CD (Continuous Delivery/Deployment)**: hasil build yang lolos otomatis disiapkan/di-deploy ke staging atau production.
>
> Alur Jenkins:
> ```
> Dev push → Git (webhook) → Jenkins Controller → Agent/Node menjalankan stages
>   [Checkout] → [Lint] → [Test] → [Build Docker image] → [Push ke registry] → [Deploy]
>                     ↓ gagal di tahap mana pun = pipeline merah, notifikasi dikirim
> ```
> Komponen penting:
> - **Controller**: otak, menjadwalkan job dan UI.
> - **Agent/Node**: mesin yang benar-benar mengeksekusi job.
> - **Pipeline**: didefinisikan di file `Jenkinsfile` yang disimpan di repo (pipeline as code).
> - **Credentials**: tempat aman menyimpan token/key (misal untuk docker login).
> - **Plugins**: ekstensi (Git, Docker, Slack, dll).
>
> Contoh `Jenkinsfile` minimal:
> ```groovy
> pipeline {
>   agent any
>   stages {
>     stage('Lint')  { steps { sh 'npm run lint' } }
>     stage('Test')  { steps { sh 'npm test' } }
>     stage('Build') { steps { sh 'docker build -t myapp:${BUILD_NUMBER} .' } }
>     stage('Push')  {
>       steps {
>         withCredentials([usernamePassword(credentialsId: 'dockerhub',
>             usernameVariable: 'U', passwordVariable: 'P')]) {
>           sh 'echo $P | docker login -u $U --password-stdin'
>           sh 'docker push myapp:${BUILD_NUMBER}'
>         }
>       }
>     }
>   }
> }
> ```
> Kaitannya dengan Q1: stage Push inilah yang sering kena throttle kalau banyak build login/pull dari satu IP.

### 3. GPG dan ASCII, cara kerjanya?

> [!answer]
> **GPG (GNU Privacy Guard)** = tool untuk **enkripsi dan tanda tangan digital** memakai kriptografi kunci publik:
> - **Public key**: dibagikan ke siapa pun, dipakai untuk *enkripsi* atau *verifikasi* tanda tangan.
> - **Private key**: rahasia, dipakai untuk *dekripsi* atau *menandatangani*.
>
> **ASCII (armor)**: output GPG aslinya biner. Opsi `--armor` / `-a` mengubahnya jadi teks ASCII (base64) berbingkai `-----BEGIN PGP ...-----`, jadi aman ditempel di email, terminal, atau file teks. Ekstensinya `.asc` (biner biasanya `.gpg`).
>
> Perintah dasar:
> ```bash
> gpg --full-generate-key               # buat keypair
> gpg --armor --export <email>          # export public key dalam bentuk teks
> gpg --import key.asc                  # impor key orang lain
> gpg --list-keys
> gpg --encrypt --armor -r <email> file.txt
> gpg --decrypt file.txt.asc
> gpg --sign / --verify                 # tanda tangan & verifikasi
> ```

### 4. Kenapa harus install key?

> [!answer]
> Untuk **memverifikasi keaslian dan integritas** software yang diunduh. Saat menambah repo (misal repo apt Docker atau Jenkins), kamu mengunduh **public key GPG** vendor. Package manager lalu mengecek tanda tangan tiap package dengan key itu:
> - Package benar-benar dari vendor (bukan palsu).
> - Isinya tidak diubah di tengah jalan (man-in-the-middle / mirror yang dibobol).
>
> Tanpa key, `apt` menolak repo dengan error `NO_PUBKEY` / "not signed". Pola install modern:
> ```bash
> curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
> ```
> `--dearmor` mengubah format ASCII `.asc` ke biner `.gpg` yang dibaca apt. Itu nyambung dengan Q3. Pastikan URL key berasal dari sumber resmi, karena key palsu = kepercayaan palsu.

### 5. Server atau service down itu seperti apa?

> [!answer]
> Gejala dari sisi user/client:
> | Gejala | Arti umum |
> |---|---|
> | Timeout / hang | Server mati, firewall memblokir, jaringan putus |
> | `Connection refused` | Mesin hidup tapi tidak ada service di port itu |
> | `502 Bad Gateway` | Reverse proxy hidup, tapi backend mati/error |
> | `503 Service Unavailable` | Overload atau sedang maintenance |
> | `504 Gateway Timeout` | Backend terlalu lama merespons |
> | `DNS_PROBE_FINISHED` / NXDOMAIN | Masalah DNS, domain tidak ter-resolve |
> | Error sertifikat | CA/TLS cert kadaluarsa |
>
> Cek cepat (urutan dari luar ke dalam):
> ```bash
> ping host                    # mesin hidup? (bisa diblok ICMP)
> nslookup domain / dig domain # DNS benar?
> nc -zv host 443              # port terbuka?
> curl -I https://domain       # status HTTP apa?
> ssh host
> systemctl status <service>   # service jalan?
> journalctl -u <service> -n 100
> docker ps -a ; docker logs <container>
> df -h ; free -m ; top        # disk penuh / RAM habis / CPU tinggi?
> ```
> Penyebab klasik: disk penuh, RAM habis (OOM killer), service crash, cert expired, deploy salah, DNS salah, firewall berubah.

### 6. FRP di github.com/fatedier/frp

> [!note] Koreksi
> Di catatan tertulis `fatedir`, yang benar kemungkinan besar **`fatedier`**.

> [!answer]
> **frp (Fast Reverse Proxy)** = tool reverse proxy yang mengekspos service di balik **NAT/firewall** (misal laptop di rumah) ke internet lewat server berIP publik (misal VPS).
>
> Dua komponen:
> - **frps** (server): jalan di VPS publik.
> - **frpc** (client): jalan di laptop/mesin lokal, membuat koneksi keluar ke frps lalu membuka "terowongan".
>
> ```
> User → VPS:6000 (frps) ══tunnel══ frpc (laptop NAT) → localhost:22 / :3000
> ```
> Contoh konfigurasi (TOML):
> ```toml
> # frps.toml (VPS)
> bindPort = 7000
>
> # frpc.toml (laptop)
> serverAddr = "IP_VPS"
> serverPort = 7000
>
> [[proxies]]
> name = "ssh"
> type = "tcp"
> localIP = "127.0.0.1"
> localPort = 22
> remotePort = 6000
> ```
> Jalankan: `./frps -c frps.toml` dan `./frpc -c frpc.toml`. Lalu `ssh -p 6000 user@IP_VPS` tembus ke laptop. Amankan dengan `auth.token` dan batasi port. Fitur lain: HTTP/HTTPS proxy dengan domain, UDP, dashboard.

### 7. Glosarium networking (versi gampang)

> Cara baca: tiap istilah dijelaskan pakai pola **masalahnya apa → analogi → contoh nyata**. Urutannya sengaja dari dasar, jadi baca dari atas.

#### 0. Dasar dulu: IP, Port, Domain

- **IP address** = alamat rumah sebuah komputer di internet. Contoh: `203.0.113.10`. Tanpa alamat ini, data ga tau mau dikirim ke mana.
- **Port** = nomor pintu di rumah itu. Satu komputer bisa jalanin banyak program sekaligus, tiap program "jaga" satu pintu. Contoh: web `80` (HTTP) dan `443` (HTTPS), SSH `22`. Alamat lengkapnya `IP:port`, misal `203.0.113.10:443` = rumah itu, pintu nomor 443.
- **Domain** = nama panggilan biar manusia ga perlu hafal angka. `example.com` jauh lebih gampang diingat daripada `203.0.113.10`.

#### 1. DNS (Domain Name System)

- **Masalah:** komputer cuma ngerti IP, manusia cuma enak ngingat nama.
- **Analogi:** buku telepon / kontak HP. Lo cari nama "Budi", dapet nomornya.
- **Cara kerja:** pas lo buka `example.com`, browser nanya server DNS "IP-nya example.com berapa?". Dijawab `203.0.113.10`. Baru browser konek ke IP itu.
- Isi "buku telepon" itu disebut **record**. Yang paling sering:
  - **A record**: nama → IP. Contoh: `example.com → 203.0.113.10`
  - **CNAME record**: nama → **nama lain** (bukan IP). Lihat bagian 2.
  - **MX record**: ke mana email untuk domain ini dikirim.
  - **TXT record**: catatan teks bebas (sering buat verifikasi kepemilikan domain).

#### 2. CNAME (kenapa ada, dan bedanya www vs tanpa www)

- **Dua hal yang beda dulu:**
  - `example.com` = domain utamanya (disebut root / apex).
  - `www.example.com` = **subdomain** (nama tambahan di depan domain utama).
  - Secara teknis keduanya **nama yang berbeda**, bisa diarahkan ke tempat yang berbeda. Biasanya orang bikin dua-duanya nunjuk ke website yang sama biar user ga nyasar. Makanya kelihatan "sama aja".
- **Masalah yang diselesaiin CNAME:** bayangin lo punya `www`, `blog`, dan `shop`, semuanya numpang di server yang sama.
  - Pakai **A record**: lo tulis IP di 3 tempat. Pas IP server ganti, lo harus edit **3 tempat**. Lupa satu = rusak.
  - Pakai **CNAME**: `www`, `blog`, `shop` lo tulis "ikut `example.com`". IP cukup diganti di **1 tempat** (di `example.com`), sisanya otomatis ikut.
- **Analogi:** di HP, kontak "Mama" lo isi "ikut nomor Bu Siti" (bukan nomornya langsung). Kalau Bu Siti ganti nomor, "Mama" otomatis ikut, lo ga perlu update.
- **Contoh nyata paling sering:** lo punya `blog.example.com` tapi blognya dihosting di GitHub Pages. Lo set `blog.example.com → CNAME → username.github.io`. Kalau GitHub pindah server dan IP-nya berubah, lo ga perlu ngapa-ngapain karena GitHub yang ngurus `username.github.io`.
- **Aturan:** CNAME **ga bisa dipakai di domain utama** (`example.com` polos), cuma di subdomain (`www`, `blog`, dll). Domain utama harus pakai A record.

#### 3. NAT (Network Address Translation)

- **Masalah:** alamat IP publik jumlahnya terbatas, dan di rumah lo punya banyak perangkat (HP, laptop, TV). Ga mungkin tiap perangkat dikasih IP publik sendiri.
- **Analogi:** kantor yang cuma punya **1 nomor telepon**, tapi ada banyak karyawan di dalam. Ada **resepsionis** (router).
  - **Karyawan telepon keluar:** resepsionis nyambungin, dan **nyatet** "Budi lagi nelpon X". Pas X ngebales, resepsionis tau harus oper ke Budi.
  - **Orang luar tiba-tiba telepon masuk:** resepsionis bingung "mau ke siapa?" dan biasanya ditolak.
- **Contoh nyata:** laptop lo di rumah punya IP internal (`192.168.1.5`), dunia luar cuma lihat 1 IP publik milik router. Laptop bisa buka YouTube (lo yang mulai), tapi orang lain ga bisa langsung SSH ke laptop lo (mereka yang mulai, resepsionis nolak).
- **Kenapa penting:** inilah alasan lo butuh *port forward* atau *tunnel* (bagian 6) kalau mau laptop di rumah bisa diakses dari luar.

#### 4. TCP dan UDP

Dua cara ngirim data. Pilih sesuai kebutuhan.

- **TCP** = **kurir paket tercatat**. Sebelum kirim, dia "salaman" dulu dengan penerima. Tiap paket dicek sampai, urutannya benar, yang hilang dikirim ulang. Aman tapi agak lambat.
  - Dipakai: buka website, SSH, download file, database (data ga boleh rusak/hilang).
- **UDP** = **lempar brosur**. Langsung kirim, ga nanya sampai atau enggak, ga ngecek urutan. Cepat tapi bisa ada yang hilang.
  - Dipakai: video call, game online, streaming live, DNS (kalau ada yang hilang ya lanjut aja, ga perlu mundur).

#### 5. Proxy: Reverse Proxy, HTTP Proxy, SOCKS

**Proxy** = perantara yang berdiri di tengah. Ada dua arah:

- **Forward proxy** (yang biasa disebut "proxy" aja): wakil di **sisi lo**. Lo nitip ke dia "tolong bukain situs X buat gw". Situs X cuma lihat si perantara, bukan lo. Contoh: VPN/proxy buat nyembunyiin IP.
- **Reverse proxy**: wakil di **sisi server**. **Analogi:** kasir/pelayan di restoran. Pelanggan ngomong ke pelayan, **ga pernah masuk ke dapur**. Pelayan yang nerusin pesanan ke dapur yang tepat dan bawa balik makanannya.
  - **Contoh nyata:** satu server punya 3 aplikasi di port berbeda (`:3000`, `:4000`, `:5000`). Nginx/Caddy dipasang di depan, pengunjung cukup buka `example.com` biasa, Nginx yang nerusin ke aplikasi yang benar. Bonus: dia juga bisa urus HTTPS (bagian 8) dan bagi beban kalau ada banyak server.

Dua jenis forward proxy yang sering disebut:
- **HTTP proxy**: kurir yang **buka dan baca amplopnya**. Dia ngerti ini permintaan web (`GET /halaman`), jadi bisa nyaring, nyimpen cache, dll. Untuk situs HTTPS, lo bilang "tolong **sambungin** gw ke situs X" (perintah `CONNECT`), lalu dia cuma jadi pipa, isi tetap terkunci.
- **SOCKS**: kurir yang **ga peduli isi paket**. Apa pun yang lo titip (web, SSH, game) diterusin mentah-mentah. Lebih fleksibel tapi ga bisa nyaring isi. Contoh: `ssh -D 1080 server` bikin SOCKS proxy lokal di port 1080 yang lewat server lo.

#### 6. Tunnel

- **Masalah:** dari bagian 3, orang luar ga bisa masuk ke laptop yang ada di belakang NAT.
- **Trik:** laptop lo yang **mulai duluan** nelpon keluar ke sebuah server publik (VPS) dan **telepon itu dibiarin nyala terus**. Karena lo yang nelpon keluar, resepsionis (NAT) ngizinin. Lalu kalau ada orang datang ke VPS, VPS ngirim permintaan mereka **lewat telepon yang masih nyala itu** ke laptop lo.
- **Analogi:** terowongan rahasia dari rumah lo ke kantor pos. Orang luar nitip surat di kantor pos, kantor pos nyodorin lewat terowongan.
- **Contoh nyata:** `frp` (pertanyaan 6), SSH tunnel, VPN, Cloudflare Tunnel.

#### 7. Multiplexing

- **Masalah:** bikin koneksi baru itu mahal (ada proses salaman, nunggu). Kalau satu halaman web butuh 50 file, bikin 50 koneksi itu boros.
- **Solusi:** pakai **satu koneksi** untuk banyak pengiriman sekaligus, tiap pengiriman dikasih label biar ga ketuker.
- **Analogi:** 1 jalan tol dilewati banyak mobil, daripada bangun 1 jalan khusus per mobil.
- **Contoh nyata:** HTTP/2 (website modern), frp (satu terowongan buat banyak service sekaligus).

#### 8. TLS, CA Certificate, dan HTTPS

- **Masalah:** data di internet lewat banyak tangan (wifi kafe, provider, dll). Kalau dikirim polos (**HTTP**), siapa pun di tengah bisa baca password lo. Ibarat **kartu pos**: semua orang yang megang bisa baca isinya.
- **TLS** = cara mengunci data. Ibarat **memasukkan surat ke kotak terkunci** yang cuma bisa dibuka penerima. Website yang pakai TLS disebut **HTTPS** (gembok di browser, port 443).
- **Tapi:** gimana browser tau yang ngobrol benar-benar `bank.com`, bukan penipu yang nyamar?
  - **Certificate (sertifikat)** = **KTP-nya website**, bilang "gw benar `bank.com`".
  - **CA (Certificate Authority)** = **Dukcapil** yang nerbitin KTP. Browser/OS lo udah punya daftar CA yang dipercaya. Kalau KTP-nya diterbitin CA tepercaya, dipercaya. Kalau ga, browser nampilin peringatan merah.
- **Cara bikin website jadi HTTPS:**
  1. Punya domain yang sudah nunjuk ke server lo (DNS).
  2. Minta sertifikat dari CA. Yang gratis dan paling umum: **Let's Encrypt** (pakai tool `certbot`, atau pakai **Caddy** yang ngurus semuanya otomatis).
  3. Pasang sertifikat di web server / reverse proxy.
  4. Buka port 443, lalu redirect HTTP (80) ke HTTPS.
  5. Sertifikat ada masa berlaku (Let's Encrypt 90 hari), jadi harus diperpanjang. Biasanya otomatis. **Kalau lupa/gagal perpanjang = website error sertifikat** (nyambung ke pertanyaan 5).

#### 9. URL Routing

- **Masalah:** satu alamat/domain, tapi di belakangnya banyak aplikasi berbeda.
- **Analogi:** papan direktori di mall. "Lantai 1 = toko A, lantai 2 = toko B".
- **Contoh nyata:** `example.com/api/...` diarahkan ke aplikasi backend, sedangkan `example.com/` diarahkan ke aplikasi frontend. Bisa juga berdasarkan nama: `blog.example.com` ke aplikasi blog, `shop.example.com` ke aplikasi toko. Biasanya dikerjain sama reverse proxy (bagian 5).

#### 10. PROXY protocol

- **Masalah:** kalau ada perantara (reverse proxy) di depan server, server cuma lihat "semua yang datang dari si perantara". IP **pengunjung asli** hilang (susah bikin log/blokir spam).
- **Analogi:** resepsionis nyambungin telepon ke bos sambil bisik dulu: "yang nelpon ini nomor 0812-xxx". Tanpa bisikan itu, bos ngira semua telepon dari resepsionis.
- **Solusi:** "PROXY protocol" = aturan bahwa perantara menaruh satu baris info di awal koneksi yang isinya IP asli pengunjung.

#### 11. QUIC

- **Masalah:** TCP + TLS itu butuh beberapa kali "salaman" sebelum data pertama bisa dikirim, dan kalau ada 1 paket hilang, semua yang di belakangnya ikut nunggu.
- **QUIC** = cara kirim data versi baru yang **dibangun di atas UDP** tapi udah punya fitur aman (TLS) dan urus-urus kehilangan paket sendiri. Salamannya lebih singkat, dan kalau satu paket hilang, yang lain tetap jalan.
- **Hasil:** website lebih cepat dibuka dan lebih tahan di jaringan jelek (misal HP pindah wifi ke 4G ga putus). **HTTP/3** = HTTP yang jalan di atas QUIC.

#### Satu cerita utuh: apa yang terjadi pas lo buka `https://blog.example.com`

1. Browser nanya **DNS**: "IP `blog.example.com`?" Mungkin lewat **CNAME** ke nama lain, ujungnya dapat IP.
2. Browser konek ke IP itu, **port 443**, lewat **TCP** (atau **QUIC** kalau didukung).
3. Browser dan server "salaman" **TLS**: server nunjukin **sertifikat** (KTP), browser cek ke daftar **CA**. Aman, lalu semua data dikunci.
4. Permintaan lo sampai ke **reverse proxy**, yang lihat host/path (**URL routing**) dan nerusin ke aplikasi blog yang tepat. Kalau perlu, dia nambahin IP asli lo (**PROXY protocol**).
5. Kalau servernya sebenarnya laptop di belakang **NAT**, ada **tunnel** yang nerusin permintaan itu ke laptop.
6. Jawaban balik lewat jalan yang sama.

### 8. Perlu belajar Docker lebih dalam

> [!answer]
> Konsep inti:
> - **Image**: template read-only (OS + app + dependency), dibuat dari `Dockerfile`.
> - **Container**: instance image yang sedang berjalan (proses terisolasi).
> - **Registry**: tempat menyimpan image (Docker Hub, GHCR, registry privat).
> - **Volume**: penyimpanan persisten di luar lifecycle container.
> - **Network**: jaringan antar-container.
> - **Compose**: mendefinisikan multi-container dalam `docker-compose.yml`.
>
> Cheat sheet:
> ```bash
> docker pull nginx
> docker run -d --name web -p 8080:80 nginx   # host:container
> docker ps -a
> docker logs -f web
> docker exec -it web sh
> docker stop web && docker rm web
> docker build -t myapp:1.0 .
> docker images ; docker rmi <image>
> docker volume ls
> docker compose up -d ; docker compose down
> docker system prune                          # bersihkan sampah
> ```
> Dockerfile contoh:
> ```dockerfile
> FROM node:20-alpine
> WORKDIR /app
> COPY package*.json ./
> RUN npm ci
> COPY . .
> CMD ["node", "index.js"]
> ```
> Urutan belajar: image vs container → Dockerfile & layer caching → volume → network → compose → multi-stage build → push ke registry (nyambung ke Jenkins & Q1).

## gogen: Go CLI untuk generate password dan ssh config

Todo dari [[03-NOV-2026#Todo]]. Project di-init dari stub `workflow/stubgo` (README bilang *Based on `workflow/stubgo@master`*).

### Requirement

![[20261103_165946.jpg]]

- `gogen -password` → generate password 16 karakter alphanumeric, output di terminal.
- `gogen -ssh -host -hostname -user -port -identityfile -savetofile` → generate ssh config. Yang tidak di-specify diisi default template (dari senior).
- Harus bisa di-`make`, binary ditaruh di `~/bin`.

### Yang dikerjakan

1. **Baca convention dulu.** Dari `go.mod`, `Makefile`, dan kode stub:
   - Go minimal **1.13**: pakai `ioutil`, tanpa `os.ReadFile` / `t.TempDir`.
   - Layout: library di root package `gogen`, binary di `./cmd/gogen`. `Version` dan `Revision` di-inject lewat `-X go.bfi.io/yourorg/gogen.Version`.
   - Doc comment di semua symbol, test pakai testify + `setUp`/`tearDown`, lint pakai `bfi-revive`.
2. **Implement.** Library (`password.go`, `ssh.go`), CLI tipis (`cmd/gogen/main.go`), plus test untuk semuanya.
3. **Makefile.**
   - Tambah target `install` → build release ke `~/bin/gogen` (override dengan `BINDIR=...`).
   - `upx` dibuat opsional. Sebelumnya `make` gagal kalau `upx` tidak terinstall.
4. **Push pertama ditolak** oleh pre-receive hook (`bfi-revive failed`):
   ```
   cmd/gogen/main.go:14:1: function run has cyclomatic complexity 12 (> max enabled 10)
   cmd/gogen/main.go:20: line is 73 characters, out of limit 72
   ```
   Fix:
   - Pecah `run` jadi `newFlagSet`, `usage`, `runVersion`, `runPassword`, `runSSH`, dan `run` jadi dispatcher (complexity tertinggi sekarang 8).
   - Rapikan semua baris > 72 karakter (tab = 4), termasuk di `ssh.go` dan test yang belum kena hook.
   - Pecah `Validate()` pakai helper `validToken`, dan ganti nama parameter `max` (builtin sejak Go 1.21).
5. **Verifikasi.** `go vet`, `gofmt`, `go test` lulus (coverage ±87% dan ±90%). `make install` lalu run dari `~/bin` jalan. Hasil lint ini dari checker tiruan, **bukan `bfi-revive` asli**.

### Struktur

```
gogen/
├── cmd/gogen/main.go       # CLI: flag parsing + dispatcher
├── cmd/gogen/main_test.go
├── gogen.go                # package doc + Dummy (stub bawaan)
├── password.go             # GeneratePassword
├── ssh.go                  # SSHConfig, Validate, String, SaveFile
├── version.go              # Version / Revision (inject saat build)
├── *_test.go
└── Makefile
```

### Cara pakai

```bash
make install                  # build ke ~/bin/gogen
gogen -password
gogen -ssh                    # default template, print ke stdout
gogen -ssh -host myserver -hostname myserver.io -user deploy -port 2222 \
    -identityfile /home/me/.ssh/id_ed25519.pub \
    -savetofile ~/.ssh/conf.d/myserver.conf
gogen -version
```

Default template (dari senior): `Host some-host-name`, `HostName 127.0.0.1`, `Port 22`, `User root`, `IdentityFile ~/.ssh/id_ed25519`. Kalau hanya `-hostname` yang diisi, `Host` ikut sama dengan hostname.

Hasil `-savetofile` otomatis bikin folder (0700) dan file (0600). Awalan `~` di `-savetofile` dan `-identityfile` di-expand sendiri.
