## 1. FRP — Cara Kerja Intinya

FRP itu **jembatan/relay**, BUKAN membuka IP lokal ke dunia. IP lokal tetep tersembunyi — yang kelihatan cuma VPS.

```
User 🌍 → VPS (frps · IP publik) ⇄ tunnel terjaga ⇄ PC lokal (frpc) → service :3000
```

- `frpc` di komputer lokal yang **initiate koneksi keluar** ke `frps` di VPS, terus koneksi dipertahankan (analogi: "nelfon duluan ke VPS dan nahan panggilannya")
- Orang dari internet akses `IP_VPS:port` → diteruskan lewat tunnel ke lokal
- Yang GAK dibutuhin: port forwarding router, IP publik dari ISP (lolos CGNAT), buka port firewall rumah
- Prinsip sama dipake: ngrok, Cloudflare Tunnel

## 2. Glosarium Konsep Jaringan

### TCP — "nelfon"
3-way handshake (`SYN → SYN-ACK → ACK`) dulu, baru ngobrol. Data dijamin nyampe, berurutan, yang hilang dikirim ulang. Dipake HTTP, SSH.

### UDP — "lempar surat"
Tanpa handshake, gak jamin nyampe, tapi cepet & ringan. Video call, game online, DNS. Frame telat 2 detik gak ada gunanya — lebih baik langsung lempar yang baru.

### Multiplexing — "1 gerbang, banyak lajur"
BUKAN buka gate baru (buka gate terus = HTTP/1.1 lama, boros). HTTP/2: banyak stream request dijerojerin dalam 1 koneksi TCP. Hemat karena bayar gerbang sekali.

### DNS — "buku telepon resmi"
Domain → IP. BUKAN alamat palsu — nama domain itu "nama panggilan resmi", IP-nya alamat asli buat mesin. Yang beneran alamat palsu itu **DNS spoofing** (buku teleponnya dimanipulasi) — itu serangan, bukan DNS-nya.

### CNAME — "alias tanpa alamat sendiri"
Papan namanya nulis: *"ini bukan toko, tanya toko sebelah."* Beda dengan cabang: cabang punya alamat sendiri, CNAME GAK punya sama sekali — dia cuma ngelempar. Analogi: sebutan jabatan "Pak Direktur" → selalu diarahkan ke orang yang sama; ganti orang, sebutan tetep. Makanya enak buat pointing ke Vercel/Cloudflare.

### NAT — "toko di kamar, penjaga pintu kaku"
- Router nyembunyiin semua device di belakang 1 IP publik
- Koneksi **keluar** bebas — penjaga nyatet di buku (NAT table), balasannya bisa nyampe ke kamar yang bener
- Orang luar yang berinisiatif duluan → penjaga: *"nyamperin kamar siapa? gak ada jadwal"* → **DITOLAK**
- Solusi: **port forwarding** (peraturan permanen) atau **FRP** (pintu belakang rahasia yang nyambung ke kantor pos/VPS)

### TLS — "kotak terkunci + cek alamat + segel"
1. **Kotak terkunci** — data dienkripsi end-to-end; bahkan anggota convoy (router/ISP) gak bisa buka, cuma pengirim & penerima punya kunci
2. **Cek alamat dulu** — verifikasi server beneran dia sebelum kirim (anti man-in-the-middle)
3. **Segel anti-bobol** — tampering di jalan terdeteksi → paket ditolak

### CA Certificate — "centang biru Instagram"
- CA = platform yang ngevouch *"akun ini beneran Apple, bukan @aple_store99"*; browser percaya centangnya karena percaya platformnya
- Self-signed certificate = centang biru bikinan Photoshop → browser nge-flash "Not Secure"
- Let's Encrypt = centang biru GRATIS, asal bisa buktiin punya domain (file unik dipasang, mereka cek)

### Proxy family — semua soal "jastip digaji siapa"

| Jenis | Analogi | Karakter |
|---|---|---|
| **Forward proxy** | Jastip digaji client | Sembunyiin client dari server; atur yang KELUAR |
| **HTTP proxy** | Jastip yang PAHAM | Baca request → bisa cache/filter/log/edit; tapi cuma terima HTTP |
| **SOCKS** | Jastip buto | Pipa murni, gak ngepeek isi; terima semua TCP (+UDP di SOCKS5) → universal |
| **Reverse proxy** | Resepsionis digaji server | Sembunyiin server dari client; atur yang MASUK (Nginx/Caddy/Cloudflare) |

- Pola: **makin paham = bisa atur tapi sempit; makin buto = gak bisa apa-apa tapi bisa lewatin apapun**
- HTTPS lewat HTTP proxy: trik **CONNECT** — proxy diminta bikin pipa polos, terus minggir (TLS dijalin langsung client↔server)
- **Proxy Protocol**: header kecil di awal koneksi *"IP asli client = X"* — biar backend tetep tahu pengunjung asli di balik proxy/LB
- **Tunnel**: paket A dibungkus dalam koneksi B (FRP, VPN)
- **URL Routing**: satu domain, arahin sesuai path (`/api` → server A, `/blog` → server B)
- **QUIC** (HTTP/3): TCP+TLS dibikin ulang di atas UDP → handshake cepet (0-RTT), bebas TCP head-of-line blocking, pindah WiFi→seluler gak putus

### Ringkasan kilat

| Konsep | Gampangnya |
|---|---|
| TCP | Nelfon: dijamin nyampe, berurutan |

## 3. OSI 7 Layer — Rak Penyimpanan Semua Konsep

OSI (Open Systems Interconnection) = model 7 lapisan yang membagi perjalanan data jaringan jadi 7 tanggung jawab terpisah. **OSI itu model/kamus, bukan software** — internet beneran jalan pake TCP/IP. Fungsinya biar semua orang pake bahasa yang sama: *"masalahnya di layer mana?"*

> [!tip] Analogi induk
> **Kirim paket Jakarta → Surabaya.** Isi paket, bungkus kado, pilihan kurir, rute antar kota, pengantaran satu gang, sampai jalanan aslinya — semuanya = 7 lapisan ini.

### Tujuh lapisan (dari isi ke jalan)

| Layer | Nama | Analogi | Isinya | Relevansi sysadmin |
|---|---|---|---|---|
| **L7** | Application | Isi paketnya | HTTP(S), DNS, SSH, SMTP | Nginx, reverse proxy, URL routing — 90% kerjaan ada di sini |
| **L6** | Presentation | Penerjemah + pembungkus kado | Encoding, kompresi, enkripsi | TLS duduk di sekitar sini (±L5) |
| **L5** | Session | Koordinator obrolan | Buka/jaga/tutup sesi, resume | Di dunia nyata tipis — diabsorpsi app & TCP |
| **L4** | Transport | Pilihan jasa kurir | TCP vs UDP, **port**, QUIC, multiplexing | `ss -tulpn` = ngintip lapisan ini; IP = alamat gedung, port = nomor loker |
| **L3** | Network | Alamat kota & peta antar kota | IP, routing, NAT, ICMP | Router, firewall IP, VPN, subnetting |
| **L2** | Data Link | Pengantaran satu gang | MAC, switch, ARP, VLAN | Ketua RT = switch, nomor rumah = MAC |
| **L1** | Physical | Jalanan & truknya | Bit, kabel, fiber, sinyal WiFi | "Layer 1 problem" = colok lagi 😄 |

### Encapsulation — perjalanan paket

```
Loe ketik: "GET /login"                      ← L7  isi
[TLS: isi diacak jadi rahasia]               ← L6  bungkus kado
[sesi dibuka & dijaga]                       ← L5  koordinasi
[TCP: pecah jadi segmen, port 443 → 80]      ← L4  kurir tercatat
[IP: alamat asal → alamat tujuan]            ← L3  alamat kota
[MAC: dari kartu WiFi → ke router]           ← L2  satu gang
0101011010... (kabel/udara)                  ← L1  jalan raya
```

Di tujuan dibongkar terbalik. Tiap lapisan nambahin "amplop"-nya sendiri (header) — kotak dalam kotak dalam kotak.

### Rak penyimpanan: konsep di catatan ini layer berapa?

| Konsep | Layer |
|---|---|
| Kabel, WiFi, sinyal | L1 |
| MAC, switch, ARP | L2 |
| IP, NAT, router, ping | L3 |
| TCP, UDP, port, multiplexing, QUIC | L4 |
| SOCKS, tunnel/FRP | L4–L5 |
| TLS, CA certificate | L5–L6 |
| DNS, HTTP(S), URL routing, reverse/HTTP proxy | L7 |

> [!note] FRP itu menarik
> Dia mulang beberapa lapisan sekaligus — tunnel-nya di L4/L5, tapi mode HTTP-nya ngerti L7. Makanya sering disebut "gabungan dari banyak konsep".

> [!important] Superpower sysadmin: troubleshoot naik tangga — MULAI DARI BAWAH
> ```
> "Loh kok gak nyambung?"
>  L1 → kabel nyolok? WiFi nempel?          ip link
>  L2 → dapat IP gak? gateway kejangkau?    ip addr, ping 192.168.1.1
>  L3 → bisa keluar jaringan?               ping 8.8.8.8
>  L4 → port-nya kebuka gak?                ss -tulpn / nc -zv host 443
>  L7 → service-nya jawab bener gak?        curl -v https://host
>  masih misteri? → Layer 8: user-nya 😄
> ```

Jump ke L7 duluan (restart nginx padahal kabel cabut) = classic rookie. Turun-naik tangga secara sadar = cara senior mikir.

### Mnemonic

- Klasik English (bawah→atas): "**P**lease **D**o **N**ot **T**hrow **S**ausage **P**izza **A**way" — Physical, Data link, Network, Transport, Session, Presentation, Application
- Indonesia (atas→bawah): "**A**yam **P**enyet **S**ambal **T**erong **N**asi **D**aging **P**entol" 🍢 — absurd = nyantol

## 4. Analogi Versi Sendiri (Hasil Ujian)

| Analogi | Nilai | Koreksi |
|---|---|---|
| TCP = tennis, UDP = squash | 8/10 | Squash bagus: main sendiri tanpa setup lawan (= tanpa handshake). Tapi bola UDP sering ilang di semak & gak peduli |
| Multiplexing = buka gate baru | 3/10 | **Kebalik.** Buka gate baru = HTTP/1.1 yang ditinggalkan. Multiplexing = 1 gate, banyak lajur |
| DNS = alamat palsu | 4/10 | Bukan palsu — penerjemah resmi. "Alamat palsu" = DNS spoofing (serangan) |
| CNAME = toko buka cabang | 6/10 | Cabang punya alamat sendiri; CNAME gak punya, cuma ngelempar |
| NAT = toko di kamar, orang ngetok → dibukain pintu | 7/10 | Jiwa bener, tapi penjaganya LEBIH kaku: yang ngetok duluan ditolak, gak ada "dibukain & diguide" — itu jasa FRP/port forwarding |
| TLS = convoy package | 7.5/10 | Tambah: kotak terkunci (bukan cuma dikawal), cek alamat dulu, segel anti-tamper |
| CA cert = centang biru Instagram | 10/10 | Perfect. Gak ada koreksi 🏆 |

## 5. Forward vs Reverse Proxy — Bedain Pake 1 Pertanyaan

> **Jastipnya digaji siapa?**

| | Forward proxy | Reverse proxy |
|---|---|---|
| Digaji oleh | Client (user) | Server (kita) |
| Posisi | Depan client | Depan server |
| Fungsi | Sembunyiin **client** dari server | Sembunyiin **server** dari client |
| Arah aturan | Yang KELUAR (egress) | Yang MASUK (ingress) |
| Contoh | Clash, `ssh -D`, Squid | Nginx, Caddy, Traefik, Cloudflare |

User pake forward proxy atau enggak = keputusan user, bukan bagian deployment server.

## 6. Arsitektur Deploy yang Bener

```
Internet 🌍
    │
    ▼
[ Cloudflare / CDN ]            ← opsional, lapisan ekstra
    │
    ▼
[ Reverse Proxy: Nginx/Caddy ]  ← SATU-SATUNYA yang nembak ke publik :443
    │
    ├─ internal → App utama   :3000  (dengerin 127.0.0.1)
    ├─ internal → API         :8000  (dengerin 127.0.0.1)
    └─ internal → Admin panel :9000  (dengerin 127.0.0.1)
```

Checklist:
- [ ] Backend bind `127.0.0.1` — BUKAN `0.0.0.0`
- [ ] Firewall cuma buka 80, 443, SSH
- [ ] TLS diterminate di reverse proxy (Let's Encrypt gratis)
- [ ] Forward proxy dalam hidup sysadmin = **egress control** (server keluar internet lewat proxy: apt mirror terkontrol, API call tercatat, malware gak bisa ngobrol ke luar)

> [!important] Prinsip besarnya
> **Tiap lapisan cuma buka mulut ke tetangganya langsung.** Publik cuma kenal Nginx, Nginx kenal backend, backend gak kenal internet. Surface area kecil = susah diserang.

## 7. Virtualisasi & Pilihan Homelab

### Tiga opsi

| | Proxmox baremetal | Debian/Ubuntu Server langsung | Proxmox di virt-manager (nested) |
|---|---|---|---|
| RAM buat lab | ~13 GB | Full 15 GB | ~5–7 GB |
| Snapshot | ✅ | ❌ → wajib backup manual | ✅✅ dua lapis (virt-manager + Proxmox) |
| Skill yang dilatih | Infrastruktur | Sysadmin OS murni | Dua dunia sekaligus |
| Risiko | Kehilangan mesin harian | Salah = betulin manual | Performance overhead |

**Keputusan: Proxmox di virt-manager (nested)** — laptop tetep jadi mesin harian, break things fearlessly berkat snapshot.

### Setup nested (kunci-kuncinya)
- Cek: `cat /sys/module/kvm_intel/parameters/nested` → harus `Y` (kalau `N`: `options kvm-intel nested=Y` di modprobe, reboot)
- virt-manager: CPU mode **host-passthrough**, 6–8 vCPU, disk qcow2 100–150 GB
- Budget RAM: host Kubuntu 4–5 GB · VM Proxmox 8–10 GB (host di dalemnya ~1.5 GB) · sisa ~5–7 GB buat VM/LXC lab
- LXC = andalan (hemat RAM, 300–500 MB/kontainer)
- ⚠️ Kubuntu suspend = seluruh lab mati → set "never sleep when plugged in"

### Catatan hardware (Vostro 14 3430 · i5-1335U)
- CPU 8/10 — 10 core/12 thread, VT-x + VT-d, U-series adem buat 24/7
- **RAM = bottleneck utama** → upgrade 2×16 GB DDR4 = upgrade paling worth it di dunia
- **WiFi = bom waktu** — bridging VM di atas WiFi sacit (mac80211 gak izinkan); solusi terbaik: **USB Ethernet adapter** ke router
- Laptop = **UPS gratis** (listrik mati, server tetep idup); set charge threshold biar baterai gak bengkak; `HandleLidSwitch=ignore`

## 8. Kenapa Server Gak Run Arch

Inti: **rolling release vs frozen release.**

- Debian/Ubuntu LTS: paket di-freeze setelah dites silang, yang di-update cuma patch keamanan, sisanya jangan diganggu 3–5 tahun
- Arch: `pacman -Syu` ngangkat SEMUA ke versi paling anyar tiap minggu — mantap buat desktop, berbahaya buat server
- **Analogi kapal**: server = kapal yang gak boleh sandar berbulan-bulan. Debian = ganti part yang retak doang. Arch = tiap minggu ganti mesin tercanggih — tiap ganti ada peluang bocor, kapten wajib standby
- Telat update di Arch = stuck & upgrade besar-besar; di Debian = cuma dapat security patch, aman
- Reproducibility: automation (Ansible, cloud image) butuh versi deterministik — "latest everything" = musuh automation
- Vendor certify di Ubuntu/RHEL/Debian dulu; produksi error di Arch = gak ada yang bisa di-tiket
- AUR = compile sembarangan = mimpi buruk audit

> [!note] Fun fact
> SteamOS = Arch-based, TAPI itu appliance: Valve freeze snapshot → uji → rilis terkontrol. Justru bukti server butuh **freeze**, bukan rolling. Dan di dunia kontainer ringan, juaranya malah **Alpine** (5 MB).

**Boring = hidup = gak bangun jam 3 pagi.**

## 9. Realita Kantor: Banyak In-House Program Itu NORMAL

- Perusahaan gede & tua akumulasi tools internal: software kemasan gak pernah cocok 100% sama proses bisnis unik → tim internal bikin sendiri → 10–20 tahun = ratusan apps
- In-house apps = **lapangan kerja sysadmin** (cloud bisa ngeluarin server, gak bisa ngeluarin 15 tahun script internal yang cuma 2 orang ngerti)
- Nilai jual = **peta**: banyak sistem gak terdokumentasi; orang yang bikin inventaris langka & cepet bernilai

> [!warning] Aturan emas hari ke-4
> **Jangan restart/service apa pun yang gak loe tahu fungsinya** sebelum tanya "ini punya siapa & siapa yang pakai." Klasik: matiin service "kayaknya gak kepake" → ternyata yang ngirim data gaji tiap tanggal 25.

Kebiasaan yang bikin bersinar: catet tiap sistem baru (nama, lokasi, owner, fungsi) · gak ada runbook → lo yang bikinin · sebelum oprek tanya: *"kalau ini mati 10 menit, siapa yang nangis?"*

## 10. Toolkit: Cara Map Service yang Jalan

> [!tip] Jenkins itu buku catatan pengiriman, bukan toko
> Jenkins tahu apa yang pernah di-build & di-deploy ke mana — tapi GAK tahu kondisi realtime (service bisa crash 3 hari setelah "success ✅", atau ada service manual yang gak pernah lewat Jenkins).

### Sweep per server (semua read-only, aman)

```bash
# 1. Semua service systemd yang jalan
systemctl list-units --type=service --state=running

# 2. 🏆 PALING PENTING: siapa megang port berapa
sudo ss -tulpn

# 3. Docker
docker ps          # yang jalan
docker ps -a       # termasuk yang mati — sering bukain kejutan

# 4. Cron — rumah script misterius
crontab -l
sudo ls /etc/cron.d/ /etc/cron.daily/

# 5. Proses teratas yang bukan service resmi
ps aux --sort=-%mem | head -20
```

`ss -tulpn` = anatomi server langsung keliatan: web di depan, app di belakang, database apa.

### Tempat in-house apps sembunyi

| Lokasi | Isi |
|---|---|
| `/etc/systemd/system/*.service` | Custom unit buatan dev (yang gak ada di `/usr/lib/systemd/`) |
| `/opt/`, `/srv/`, `/home/*/apps` | Folder aplikasi internal |
| `/etc/nginx/sites-enabled/` | Tiap vhost ≈ satu app |
| `docker-compose.yml` tersebar | `find / -name "docker-compose.yml" 2>/dev/null` |
| `pm2 list` / `supervisorctl status` | Node apps / process manager |

### Cross-reference Jenkins ↔ server
- Ada di Jenkins tapi GAK running = **service mati** (temuan #1)
- Running tapi GAK ada di Jenkins = **service hantu manual** (temuan yang lebih seru 👻)

### Playbook minggu pertama
1. Minta akses SSH read-only ke server utama
2. Sweep tiap server: `ss -tulpn` → `systemctl` → `docker ps` → `crontab -l`
3. Buka Jenkins → catat daftar job & server target deploy
4. Samain catatannya → jadi inventaris: nama, lokasi, owner, fungsi
5. Temuan aneh → tanya senior: *"ini perlu tetep jalan gak?"*

> [!danger] Selama fase eksplorasi
> Gak ada satu pun command `stop`/`restart`/`kill` yang keluar dari jari. Liat, catet, tanya.
